Option 1: Agent Systems

1Main Post
Most production LangGraph deployments avoid SQLite checkpointing entirely. Multiple workers corrupt the store with race conditions. We run Redis Streams with Lua scripts to serialize state writes. Each checkpoint is a JSON blob with a monotonically increasing counter. Works at 500 RPS with zero lost state.

The real win is separating checkpointer from graph service entirely. Let a dedicated actor own state mutations. Never let two LLM instances compete for the same checkpoint.

Option 2: RAG Systems

2Main Post
Building a RAG pipeline with LangGraph exposed a hidden bottleneck: checkpointing 50K documents. SQLite chokes on concurrent reads. We switched to ChromaDB's vector store as the checkpointer. The document embeddings ARE the state. No separate checkpoint layer needed. 3x throughput, half the latency.

Option 3: FastAPI Backends

3Main Post
LangGraph checkpointers are synchronous. Your FastAPI endpoint blocks on disk I/O. We moved checkpointing to a background worker with message queues. Graph returns `checkpoint_required=True` in the response. Client polls or receives websocket push. 120ms median save time becomes 5ms endpoint latency.

Option 4: LLM Inference

4Main Post
Running LangGraph with 4050 context windows means checkpointing entire conversation history. SQLite writes balloon to 50MB per checkpoint. We chunk state: recent turns in checkpointer, older turns in object storage. Each checkpoint is a 2KB pointer plus metadata. Cost drops 83%.
276/280 ✓
Reply
Lesson: checkpointing is state management, not persistence. Don't pickle the whole graph. Store references, not values. Let each node decide what needs durable storage. The framework should orchestrate, not hoard data.
