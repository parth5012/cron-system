Most RAG applications fail in production not because the LLM is dumb, but because naive cosine vector search is fundamentally flawed.

If your RAG system hallucinates on keyword-heavy queries or specific IDs, here is the exact hybrid architecture you need: 🧵👇

2/7

1️⃣ The Flaw with Vector-Only Search

Vector embeddings capture semantic "vibe", but fail at exact matches: product codes, error tracebacks, acronyms, or numbers.

The fix? Hybrid Search: Combine Dense Retrieval (pgvector with HNSW) + Sparse Retrieval (pg_trgm / Postgres Full-Text tsvector).

3/7

2️⃣ Reciprocal Rank Fusion (RRF)

Don't just add scores together—their scales differ.

Use RRF to normalize and combine dense and sparse rankings:

RRF_Score(d) = Σ [1 / (k + rank_i(d))] (where k ≈ 60)

This gives you both conceptual relevance AND exact keyword precision.

4/7

3️⃣ Two-Stage Retrieval & Cross-Encoder Reranking

Never feed 50 raw chunks directly to the LLM context.

• Stage 1: Fetch Top 30 candidate chunks using Hybrid RRF.
• Stage 2: Pass candidates through a Cross-Encoder reranker (like BAAI/bge-reranker or Cohere).
• Stage 3: Send only the Top 4 purest chunks to the LLM.

5/7

4️⃣ Asynchronous Ingestion with FastAPI & Task Queues

Never chunk & embed synchronously in your HTTP route handler.

• FastAPI endpoint receives doc → Stores metadata in Postgres → Dispatches background worker (Celery/Redis/ARQ).
• Worker handles chunking, batch embedding generation, and pgvector upserts.

6/7

5️⃣ Metadata Filtering & Partitioning

Scale your vector searches by partitioning pgvector indexes by tenant_id or org_id.

Pre-filtering before the vector distance scan shrinks search space by 90%+ and drops query latency from 180ms to <15ms.

7/7
