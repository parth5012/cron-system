Pi Durable — Deep Research Report

How durable agents work (earendil-works/pi) and how to apply them to the fleet and AI-OS projects.

Sources: GitHub packages/durable README + spec.md · Syntax video "You need to check out Pi Durable" (youtu.be/BLRReTwV8Fc) · flaviocopes tutorial · MindStudio explainer · Date: 2026-10-17

1. What Pi Durable is

An experimental TypeScript library for building durable agents: conversations, model turns, tool calls, and app state are committed to storage before anything is shown, so a crashed/restarted process reopens storage and resumes unfinished work where it stopped.

Mental model: a database file + a conversation. Submit work with an ID; tools are plain functions. The harness saves everything as it goes.

2. The problem it solves

Agents now run for an hour, start on their own (webhook/cron), and do things that can't happen twice (email, PR, charge). If one crashes mid-run, you must manually check what broke overnight. Durable agents must: keep working, be resumable, know the exact step, and not repeat side-effecting steps.

Syntax author deleted ~8,000 lines of brittle custom agent plumbing after adopting Pi Durable and got a better system for free.

4. Durability mechanics

  • Persist & resume: SQLite/JSONL. harness.resume() continues unfinished runs. Submitting/waiting also starts scheduler.
  • Provider identity: persisted UUIDv7 in pi.provider → pi-ai sessionId for prompt-cache/session affinity. Survives reopen/retry/reset/compaction/model change; child/fork gets fresh identity.
  • Idempotent submission: same requestId returns existing submission instead of submitting twice. harness.submission(id) reacquires after restart.
  • Task checkpoints: each task saves checkpoint each step. abandonOnRestart: true auto-aborts tasks whose creator never resumes.

5. Tools & replay safety (the key design)

Each tool call is its own durable task; intent committed before execute(). If process dies mid-call, tool reruns on reopen only when declared replay: "safe"; otherwise model gets an interrupted error result with committed output. Default policy is unsafe.

OperationReplay?
Read service statussafe answer may change
Search issuessafe no mutation; may cost money
Send emailunsafe unless sender dedups operation ID
Create PRunsafe unless app finds/reuses existing PR
Deploy releaseunsafe unless deploy system reconciles

Caveat: requestId dedup stops duplicate admission of a submission; it does not guarantee external actions happen exactly once. Tool authors must declare replay-safe only when repeated execution is safe; for side-effecting tools use operation IDs + external idempotency or reconcile before retry.

Nested tool calls via api.executeTool(); callers controls who may call a tool (model/tools/both); modelTools narrows what model is offered; deferred + tool_search for large sets.

6. Code Mode

@earendil-works/pi-durable/codemode adds a codemode tool: model writes JS calling conversation tools as await tools.<name>(args) in a QuickJS sandbox. Script survives restart (resumes where it was) via a journal of results. Deterministic sandbox (virtual clock, seeded randomness, UTC). store/load keep JSON per conversation. Cloudflare: RemoteCodemodeSandbox.

7. Compaction & context limits

Persistence ≠ unlimited memory. Long conversations still bound by model context window. Supports manual compact() and auto-compaction via settings (reserveTokens, keepRecentTokens, backgroundTokens, modelOverrides). On provider overflow, generation compacts and retries once. Advice: store facts that must be preserved in structured documents/DB, not rely on summary.

8. Multi-conversation, forks, subagents, child tasks

  • Multiple conversations per harness, each with own model/tools/instructions/cwd.
  • Fork at a point → continues independently; keeps parent's agent at fork entry; fresh provider identity.
  • Subagents: a tool creates a child conversation owned by its task. Foreground (parent idle only once child done, abort propagates) and background (owned by anchor task, survives parent abort). Examples 22/23.
  • Child tasks: own child tasks + waiting state (allSettled/failFast), completing, bottom-up abort. Example 24.
  • Task graph: harness.taskGraph() / watchTaskGraph() for monitoring.

9. Watching / UI / multiplayer

  • viewState() subscribable view (entries, docs, inbox, usage, agent, provider); watch() delivers exact Chord ops per commit.
  • watchEvents() (experimental) gives coding-agent style events.
  • Multiple clients connect to same harness → observe, steer, add follow-up. "Multiplayer comes for free."
  • Steering: whenBusy: "steer" places input after current tool round; follow-up (default) when run answers; writes can happen mid-run.
  • Environment per call: NodeExecutionEnv (cwd) or custom (container per conversation).

10. Storage trade-offs & caveats

  • Backends: memory (no persistence, tests), SQLite (node), JSONL.
  • One process owns a storage backend at a time — no cross-process locking.
  • Default SQLite uses WAL with synchronous=NORMAL → process crash recoverable, but power/host failure can lose newest commits. Reconfigure for strict durability.
  • APIs experimental → budget time to revisit.
  • Tool authors must explicitly mark replay-safe for auto-recovery.
  • Context limits still apply (compaction is the mitigation).

11. Where it runs (video)

Anywhere JavaScript runs: browser (IndexedDB — Mario's phone agent, 100% on Android except model calls), Node (Mac Mini + SQLite), Cloudflare Durable Objects, Deno's cld. Not locked to one provider. 13. Applying to the FLEET project

High fit Fleet = always-on Linux boxes running agents; brains = laptop orchestrator; send work, close lid, work keeps running — exactly Pi Durable's deployment shape.

  • Self-healing agent on box-1 (video's pattern): webhook → durable conversation → triage → fix → PR → resolve. Stable requestId from alert event id. Read tools safe; write tools (git/PR) unsafe with idempotency guards.
  • Durable long-running jobs (omniroute/secondbrain sync, backups): wrap orchestration as durable agent so a crash mid-sync resumes instead of leaving partial state. Keep Python for actual DB ops; agent drives via tools.
  • Multi-client steering from phone/laptop maps directly to Pi Durable multiplayer model.
  • Subagents for parallel worktrees (fleet already uses worktrees) with durable ownership + bottom-up abort.
  • Monitoring dashboard via taskGraph() + watch()/watchEvents() → fleet-status view.
  • Per-box ownership: one process per box owns its SQLite; don't share a DB across processes. Back up DBs alongside existing backup scripts.
  • Tool replay discipline: classify every fleet tool; document in AGENTS.md.

Adoption path (fleet)

  1. Phase 0: Run flaviocopes demo on box-1 to validate crash recovery on real hardware.
  2. Phase 1: One self-healing flow (fleet-status failure → investigate logs → report), read-only tools first, cron-system webhook trigger.
  3. Phase 2: Add write tools (git commit/push/PR) with idempotency guards + human approval hook.
  4. Phase 3: Migrate one long-running script family to be driven by durable agent.
  5. Phase 4: Multi-client UI (phone) + task graph dashboard.

14. Applying to the AI-OS project

Medium-High fit (runtime layer) AI-OS is Python-centric and documentation/context-heavy. Pi Durable is TS/Node. Don't rewrite working Python automations. Instead:

  • Add a durable "always-on personal agent" on box-1 (via fleet) triggered by cron-system/T3 scheduler; conversations per domain (freelance digest, internship learning, second-brain ingestion, daily planning); stable requestIds from event ids.
  • Second-brain ingestion as durable agent: long-running read→atomic-notes runs survive laptop sleep; compaction handles long context; structured documents track ingested sources.
  • Freelance bid flow durability: multi-step flow holds state across sessions; per-job state as a Pi Durable document.
  • Learning/portfolio value: building a durable-agent demo is a strong portfolio piece and exercises agent-harness engineering (a stated skill); could become a freelance offering.
  • Context-engineering alignment: AI-OS context docs + Pi Durable structured documents fit together; store priorities/decisions as docs agents read.
  • Do not migrate: keep cron-system as trigger/scheduler; use Pi Durable agents as the worker. Bridge to Obsidian by a tool writing to the vault path.

Adoption path (AI-OS)

  1. Phase 0: Read pi-durable examples folder with an agent; run flaviocopes crash demo.
  2. Phase 1: One durable agent for one repetitive task (freelance digest triage or ingest-media), read-only first.
  3. Phase 2: Add write tools with approval hooks; multi-client steering.
  4. Phase 3: Integrate with Obsidian second brain (agent writes notes).
  5. Phase 4: Consider offering durable-agent dev as freelance service.

15. Decision summary

  • Pi Durable is the right abstraction for "agents that must survive crashes and run unattended" — fleet's mission and AI-OS's automation ambition.
  • It does not solve context limits, external-action exactly-once, or multi-process storage ownership. Design around those.
  • Best adoption: pilot narrowly (one self-healing/read-only flow on box-1), validate crash recovery on real hardware, then expand. Don't big-bang migrate Python automations.
  • Biggest immediate value for Parth: (1) hands-on learning/portfolio, (2) unattended self-healing agent on fleet box-1, (3) durable long-running ingestion for second brain.
