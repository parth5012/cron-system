Definition

What is a Subquery?

A subquery is a SELECT statement nested inside another SQL statement. Also called: inner query, nested query, or sub-SELECT.

Key principle: The inner query is executed first, then the outer query uses its results.

Classification

Types of Subqueries

Scalar

Returns Single Value

SELECT name FROM employees WHERE salary > (SELECT AVG(salary) FROM employees)

Row

Returns Single Row

SELECT * FROM employees WHERE (dept_id, salary) = (SELECT department_id, MAX(salary) FROM employees WHERE name = 'John')

Table

Returns Multiple Rows

SELECT * FROM employees WHERE department_id IN (SELECT department_id FROM departments WHERE location = 'NYC')

Four Main Types 05 / 17
Advanced Type

Correlated Subqueries

Correlated subqueries depend on the outer query - they're executed once per row in the outer query. 

-- Example: Find employees earning above their department average
SELECT e1.name, e1.salary 
FROM employees e1 
WHERE e1.salary > (
    SELECT AVG(e2.salary) 
    FROM employees e2 
    WHERE e2.department_id = e1.department_id
);
Execution Order 06 / 17
Comparison

When to Use Subqueries vs JOINs

✅ Use Subqueries

WHEN:

  • You need aggregated data for filtering
  • Checking existence of records
  • Simplifying complex queries
  • Filtering based on calculated values
❌ Avoid Subqueries

WHEN:

  • Simple joins solve the problem
  • Performance is critical
  • Multiple tables need joining
  • Same data accessed repeatedly
💡 Pro Tip

EXISTS is often faster

EXISTS is faster than IN for checking row existence

Performance Tips

Best Practices & Performance Tips

  • ✅ Index the columns used in subquery conditions
  • ✅ Use EXISTS instead of IN for large datasets
  • ✅ Limit subqueries to necessary scope
  • ✅ Consider JOINs when performance is critical
  • ✅ Use aliases to make correlated subqueries readable
  • ✅ Avoid correlated subqueries in large datasets
  • ✅ Test with EXPLAIN to see execution plan

Error Prevention

Common Pitfalls & How to Avoid Them

❌ Multiple Rows Error

-- Problem: Subquery returns more than one value -- Fix: Ensure single value or use IN

❌ NULL Handling with NOT IN

-- Problem: NOT IN with NULLs returns nothing -- Fix: Use NOT EXISTS or add 'AND column IS NOT NULL' condition

❌ Ambiguous Columns

-- Problem: Column name confusion in joins -- Fix: Always qualify with table aliases (e1.salary vs e2.salary)

Comparison

EXISTS vs IN: Which to Choose?

EXISTS

Better For:

  • Existence checks
  • Large datasets
  • Performance
  • NULL-safe operations
IN

Better For:

  • Simple membership tests
  • Small result sets
  • Readability
  • When you need the actual values
